# S0 — execution/recovery feasibility spike

Tracked by [#1](https://github.com/mhingston/pits/issues/1), [#2](https://github.com/mhingston/pits/issues/2), [#3](https://github.com/mhingston/pits/issues/3).

## Intent

This branch implements the S0 execution/recovery feasibility spike. It
co-locates PiHarness and Sandbox 1.0 in one Durable Object and prototypes
fail-closed process intents, checkpoint/restore, and backup retention. All S0 acceptance work and disposable-resource cleanup are complete. The
final repository/retention and 10-iteration recovery validation is recorded
below. PR #8 is for review; do not merge automatically. This remains a headless,
restricted-command experiment, not a production multi-user agent service.

## Trust boundaries

- Durable Object SQLite records command intent, active-command gate, receipts,
  container boot ID, and committed workspace-checkpoint metadata.
- Container runs with `enableInternet: false` for S0 and has no provider or
  GitHub credentials.
- Container-local `mkdir` reservations guard against duplicate launches
  *within the same boot*; they are deliberately outside backed-up workspace.
- A new boot invalidates the old container command identity. We never blindly
  replay an in-flight command on the new instance.
- A non-atomic R2 backup plus SQLite metadata update is treated as a two-phase
  protocol. We can only restore a **committed** backup handle.
- Checkpoint metadata records the Pi session ID, active-transcript tail entry ID,
  and entry count. Restore resets the active Pi transcript with an explicit
  recovery handoff so post-checkpoint tool output is not treated as current state.
- Lost command-receipt sequence ranges are retained across later restores; an
  older receipt cannot become successful again just because a newer checkpoint
  was created.
- Worker requests use `ctx.exports.PitsAgent`, the loopback namespace for the
  same exported class, to resolve the current implementation. The test harness
  checks the Worker source revision and DO checkpoint protocol before running.
- Cloudflare Lifecycle is the only owner of the Durable Object alarm. No
  custom `setAlarm` call is allowed.

## Must-pass injected failure tests

1. Repeat the same `id` with the same payload. Observe **one** appended
   marker, not just one final file (`touch` would miss duplication).
2. Restart/redeploy the Task DO during an active command; verify the container
   boot stays the same, and reattach/poll collects exactly one exit result.
3. Inject a DO abort before intent, after intent, after `mkdir`, immediately
   after launch, after process exit but before receipt, and after receipt but
   before response delivery.
4. Destroy the container mid-command. The replay must say **lost**, must not
   re-dispatch, and must block new edits until a known checkpoint is restored.
5. Restore the last committed backup; compare Git status and file hashes
   against the checkpoint's recorded state.
6. Interrupt backup before metadata commit. Previous checkpoint remains valid.
7. Quiescence: an in-flight command blocks both another mutation and backup.
   S0 accepts only a bounded list of foreground coreutils commands, simple
   workspace file operations, and `&&`; shell interpreters, pipes, expansions,
   redirections outside `/workspace/pits`, and background forms are rejected.

## Validated behavior and remaining limitations

- The live repeatable suite exercised PiHarness, the native container, and the
  exported `DirectoryBackupGateway` in the same DO. See the run record below.
- `unknown` keeps the active lock. The same command ID may observe its original
  process and collect a late result; a different mutation is rejected. If the
  process cannot be classified, manual workspace restore and reconciliation
  remain required.
- S0 is not a general shell. Requests are restricted to a bounded foreground
  command grammar and a single foreground process; tests reject shell
  interpreters, pipes, expansions, background jobs, path escapes, and other
  detached-writer forms. The runner is not a security boundary for arbitrary
  processes or preloaded workspace content outside this API.
- Live tests verified the transcript anchor and recovery handoff (`pi.reset`)
  after restore. Checkpoints now record Git HEAD/tree/status alongside the
  transcript anchor and archive SHA-256; see the identity decision below.
- The original recovery-matrix checkpoint was only 344 bytes. The suite exercises a
  64 MiB mutation fixture during interrupted transfer, but aborts before a
  representative large backup can commit. The later focused representative run
  below commits an 84 MB archive. Do not extrapolate the original measured
  latency/size to a real repository.
- The deterministic `@earendil-works/pi-ai` Faux provider is enabled only by
  the test config; no model request or model cost was incurred. `/api/ask`
  remains separately gated by `PITS_ENABLE_MODEL`.
- R2 lifecycle aborts incomplete multipart uploads separately. Completed
  backups now use per-DO prefixes and are collected under the maintenance
  lock after a 24-hour grace, protecting current and restored checkpoint
  handles. Legacy shared-prefix objects are never automatically collected.
  See the retention contract below.
- Cloudflare Access was not configured. The operator chose bearer-only for
  this short-lived deployment; do not copy that posture to a public or
  persistent environment.
- `npm audit` previously reported three high-severity transitive findings in
  MCP OAuth client/SDK versions pinned by `agents@0.28.0` (GHSA-6qxp-vccf-f47h).
  S0 does not configure MCP and the execution container has no Internet, but
  the upstream dependency risk remains for a future network-enabled agent.
- Restore plus reconciliation controls workspace-visible mutations; it cannot
  undo external side effects performed outside the restricted S0 command API.

## Current fail-closed recovery protocol

- Shell command IDs are hashes of Pi task IDs (or a manual test probe ID).
  Repeated command IDs with **different payloads** are rejected, including
  when a previous successful receipt exists.
- Pi's `sandbox_bash` tool uses `replay: "safe"` only to re-enter the durable
  runner adapter after interruption. The runner's stable Pi task ID, payload
  digest, same-boot process reservation and no-redispatch gate—not blind shell
  replay—must prove safe reattachment in the live test before acceptance. The
  Pi adapter also re-observes ambiguous same-ID commands for a bounded four
  minutes, covering commands that exit after the runner's 120-second poll.
  The manual `/api/probe` path separately tests the adapter without relying on
  a model.
- The working directory is `/workspace/pits`, created at runtime. The
  reservation directories live outside it and are not included in backups.
- Checkpoints capture the sequence number of the last completed command.
  On restoration, receipts for commands completed *after* the checkpoint,
  but *before* restoration, become explicitly **lost**; they are never
  silently presented as still applicable. New commands after reconciliation
  have later sequence numbers and are allowed.
- A restored workspace has `reconciliationRequired: true` until a human
  checks it and acknowledges the exact backup ID. This is **not** automatic
  consistency verification or a transcript-entry checkpoint.

## Checkpoint identity and completed orphan retention decision

S0 checkpoints now capture Git HEAD, its tree ID, and porcelain status under
the same workspace maintenance lock as the archive and transcript anchor.
A workspace without Git is explicitly recorded as `not-a-repository`; an
unborn repository has a null HEAD/tree. Git tree identity describes committed
files only. The backup record's SHA-256 binds the actual archive, including
`.git`, dirty tracked files and untracked files that are not excluded. A
separate dirty-tree Git commit is not required: it would modify the workspace
and would still miss untracked content. Restore/reconciliation must compare
Git state and relevant content, and the SDK verifies archive size and SHA-256.
This is a quiesced snapshot contract, not an atomic transaction with Pi.

Completed objects must **not** have an expiration lifecycle rule on the shared
`pits-s0/` prefix: a still-current checkpoint may be arbitrarily old. R2's
incomplete multipart abort rule is retained separately.

New checkpoints use `pits-s0/owners/<DurableObject-ID>/`. The owning DO is the
only checkpoint writer/collector for that prefix, so a bucket-wide DO inventory
is unnecessary. Under its maintenance lock, the collector paginates all owned
archives and marks `checkpoint.backup` and `restored-checkpoint.backup` as
protected. Only unreferenced, correctly named archive objects uploaded more
than 24 hours ago are deleted. New uploads from a helper whose DO died cannot
commit SQLite metadata; their completion timestamp gives them a fresh grace.
No backup collector uses an alarm; PiHarness Lifecycle retains alarm ownership.

Collection runs after a successful checkpoint and through authenticated
`POST /api/backups/collect`. A checkpoint stays committed if subsequent
collection fails; diagnostic timestamps are persisted and the next collection
retries. The explicit collector returns an error on storage failure. Idle DOs
retain orphans until a checkpoint or maintenance request; a deployment can
schedule requests externally without taking over the Lifecycle alarm.

Checkpoint metadata commits its monotonically increasing `generation` in the
same SQLite transaction as the checkpoint record. Command `sequence` remains a
separate receipt-divergence boundary. Git status uses pathspecs that omit the
same dependency/cache subtrees as the archive, so discarded caches are not
misrepresented as preserved workspace state. HEAD and tree identity still
refer to the repository's committed tree; archive SHA-256 binds dirty and
untracked contents. A tracked file deliberately placed in an excluded subtree
will be absent after restore; those subtrees must contain disposable data.

Legacy checkpoints without a prefix remain restorable through `pits-s0/`.
Automatic collection never scans that shared legacy prefix. Retire legacy
archives only after disabling all writers and confirming no eligible checkpoint
references remain. Retiring the entire dedicated test bucket after deleting its
Worker and Container makes every test archive unreferenced; preserve evidence,
delete completed objects, abort listed incomplete uploads, verify both lists
are empty, then delete the bucket. No production bucket is changed by this
spike cleanup.

A normal age-only R2 expiration rule cannot express SQLite reachability. The
completed-backup requirement is therefore implemented with owner-scoped
collection, while R2 lifecycle handles incomplete multipart uploads. Applying
an expiration rule to current checkpoint archives would delete recoverable
state, so no such rule is installed.

### Deployment routing correction

During continuation, repeated code-changing deployments updated the default
Worker while the `env.PITS` binding continued to serve older PitsAgent method
behavior. The convergence guard caught this rather than validating stale code.
Routing through the documented same-Worker `ctx.exports.PitsAgent` loopback
namespace resolved the protocol check on the existing test deployment; no
second Sandbox DO class was added. See [Cloudflare's loopback namespace example](https://developers.cloudflare.com/cf/projects/cloudflare-config/).

checkpoint status is scoped to backed-up paths. Failed attempts remain in the
local artifacts and are not counted as passing evidence.
